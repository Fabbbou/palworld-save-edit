# ADR-001: Oodle decompression crate

## Decision

Use `oozextract` (pure Rust) for PlM/Oodle Mermaid decompression. Rejected `oozle`.

## Why

`oozle` wraps the C/C++ reference `ooz` decompressor via `cxx`. Adding it as a
dependency pulls in `cxx-build`/`cxxbridge` and a C++ compiler at build time.
Confirmed by trying it: `cargo build -p palsave --target wasm32-unknown-unknown`
failed —

```
cargo:warning=Compiler family detection failed due to error:
ToolNotFound: failed to find tool "clang++": No such file or directory (os error 2)
```

`wasm32-unknown-unknown` has no C++ toolchain and no way to get one on a static host.
`oozle` is disqualified outright for this project, not just less convenient.

`oozextract` is pure Rust, ports the open-source `ooz` algorithm directly, and with
`default-features = false` (dropping the `x86_sse` SIMD path, `cli`, `async`, `tokio`
features) it compiles clean for `wasm32-unknown-unknown` with no extra tooling:

```
cargo build -p palsave --target wasm32-unknown-unknown
   Finished `dev` profile [unoptimized + debuginfo] target(s)
```

Its public API is slice-based (`Extractor::read_from_slice(&self, input: &[u8],
output: &mut [u8]) -> Result<usize, OozError>`), no `std::fs` or threads required for
actual use — matches the "borrow, don't clone", single-threaded, lazy design this
project needs. Its own test suite (not run as a dependency, but present in the crate)
carries `testdata/`/`verify/` fixture pairs for Kraken/Mermaid/Selkie/Leviathan/LZNA/
Bitknit, which is the best available confidence the decoder itself is correct.

## Open question — resolved against real fixtures

The container header carries one `save_type` byte (0x31 = one compression pass,
0x32 = two) shared across both PlZ and PlM magics. For PlZ, pass 2 is a second zlib
inflate over the result of pass 1 — well-documented, easy to synthesize and round-trip
test with no real fixture required.

For PlM, whether `save_type` 0x32 ever occurs was unverified pending a real fixture.
Resolved: five real saves (`Level.sav`, `LevelMeta.sav`, `LocalData.sav`,
`WorldOption.sav`, one `Players/*.sav`), all PlM, all `save_type` 0x31. Engine version
5.1.1 across all of them. `container_round_trips_on_every_fixture` and
`gvas_parses_and_round_trips_on_every_fixture` in
`crates/palsave/tests/fixtures.rs` are green against all five —
decode → encode → decode and GVAS parse → write are both byte-identical.

`ContainerError::UnsupportedOodleDoublePass` is left in place as a guard: if a future
fixture (a different game version, or a Game Pass CNK-wrapped save) turns out to use
PlM with `save_type` 0x32, it'll fail loudly here instead of silently guessing a
buffer size, per the "never guess" rule in `CLAUDE.md`.
