# ADR-004: The splice engine (Phase 4)

## Status

Done. `crates/palsave/src/edit/`. Gate green:
`renaming_a_guild_leaves_every_unrelated_byte_identical` in
`crates/palsave/tests/fixtures.rs`.

## The shape of the problem

Everything before this phase was read-only, and read-only work could lean on one
simplification: `GvasFile::write` concatenates the original spans, so round-tripping
is correct *by construction* — no property is ever re-derived from a decoded value.
Editing breaks that. A changed value has a different length, and a GVAS property tag
carries a u32 `size` giving the byte length of the value that follows it. Change one
value and every enclosing property's `size` is now a lie.

What turned out **not** to need fixing is as important as what does. Struct bodies
are None-terminated with no length prefix. Map entries have no per-entry length.
Array elements have no per-element length. So for an in-place value swap, the
complete set of fixups is: patch the `size` field of the edited property and of each
of its ancestors, all by the same delta. Nothing else in the format encodes a length
that an in-place edit can invalidate.

That makes every edit expressible as a set of byte-range replacements against the
original buffer — including the fixups themselves, since a `size` field is just four
bytes at a known offset. Which is the whole design:

```
SpliceSet { Vec<Splice { range: Range<usize>, bytes: Vec<u8> }> }
  .apply(source) -> sort by start, reject overlaps, emit chunks, one final copy
```

Untouched regions are `memcpy`'d straight from the source and never re-encoded.
Renaming one guild rewrites ~4.7 KB of `GroupSaveDataMap` and patches three 4-byte
size fields; the ~6 MB `MapObjectSaveData` sibling is copied verbatim, exactly as the
project plan requires.

`replace_property_value(source, chain, new_value, has_property_guid)` takes the
ancestor chain outermost-first (e.g. `[worldSaveData, GroupSaveDataMap, RawData]`)
and produces that whole splice set. It *checks* the chain is genuinely nested rather
than assuming it: a caller assembling a chain from separate `materialize` calls could
easily pass siblings by mistake, and the resulting save would be quietly corrupt.

## Verification, and proving the test isn't vacuous

`edit::verify_reparses` re-parses an edited buffer and asserts the parse partitions
it exactly — `GvasFile::parse(bytes).write() == bytes`. That equality holds only if
every `size` field agrees with the real byte layout at every level, which makes it a
strong, cheap check for exactly the failure mode this phase introduces. `CLAUDE.md`
calls losing a world to a silent encoder bug "the failure mode that actually
matters"; this is the check that makes it loud.

Two deliberate choices keep the gate test honest:

1. **The rename changes length** (the fixture's 14-char guild name → a 37-char
   one, +23 bytes). A
   same-length rename would pass even with the size-fixup logic entirely absent.
2. **The test was verified to fail when the code is broken.** Temporarily changing
   the fixup loop to `chain.iter().skip(1)` — dropping only the outermost
   `worldSaveData` fixup — made it fail immediately at `verify_reparses` with
   `UnexpectedEof { need: 256, at: 8535390, have: 32 }`. Reverted after confirming.

The gate itself compares *content*, not offsets: an edit that changes a length shifts
every absolute offset after it, so "unrelated bytes identical" can only meaningfully
mean each unrelated property's bytes are unchanged. The test extracts all 22
`worldSaveData` children before and after and asserts exactly one — `GroupSaveDataMap`
— differs.

## Deliberately not supported yet

Adding or removing map entries or array elements. Those additionally change a count
field, which is a different fixup with different failure modes.
`replace_property_value` only swaps one value for another, and nothing in the API
pretends otherwise.
