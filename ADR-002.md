# ADR-002: GroupSaveDataMap RawData — format drift, and its resolution

## Status

Resolved. `crates/palsave/src/rawdata/group.rs` decodes and round-trips all 8 real
groups in `fixtures/Level.sav` byte-identically (`group_rawdata_round_trips_on_level_sav`
in `crates/palsave/tests/fixtures.rs`).

## The problem

cheahjs/palworld-save-tools' `rawdata/group.py` — the only spec the project plan
named for this format — is unchanged upstream since **2024-02-03** (confirmed via
`GET /repos/cheahjs/palworld-save-tools/commits?path=palworld_save_tools/rawdata/group.py`,
no newer commit exists). Against `fixtures/Level.sav` (engine 5.1.1, a materially
newer Palworld build), it decoded the common header correctly — `group_id`,
`group_name`, and a 137-entry `individual_character_handle_ids` list all traced out
field-by-field exactly as expected — but diverged immediately after: reading a
`u32` array count landed on values in the billions for both `Organization`-family
`base_ids` and `Guild`-family `map_object_instance_ids_base_camp_points`. Manually
diffing the 7 real `Organization` blobs byte-by-byte (identical except for `group_id`
and one incrementing byte) confirmed this wasn't a transcription error — the wire
format genuinely doesn't match the Feb-2024 reference anymore, exactly the version
drift `CLAUDE.md` warns to expect.

## How it was resolved

Manual reverse-engineering from the byte diff got close (correctly isolated the
extra bytes' position and size) but not to a confirmed field-level answer — two
plausible boundary interpretations fit the `Organization` bytes equally well, and
guessing between them would have been exactly the "plausible-looking wrong answer"
`CLAUDE.md` forbids.

Instead: searched GitHub code search (`gh api search/code`, authenticated) for the
literal field name `map_object_instance_ids_base_camp_points`, which turned up
**`oMaN-Rod/uesave-rs`** (branch `pluggable-game-support`) and its consumer
**`oMaN-Rod/palworld-save-pal`** — both pushed within the day this was investigated.
That fork extends `trumank/uesave-rs` with a pluggable per-game struct system and has
a fully typed, actively-maintained `PalGuildGroup`/`PalOrganizationGroup`/
`PalIndependentGuildGroup` implementation in
`uesave/src/games/palworld/groups.rs`. Its layout, verified field-by-field against
the real `Guild` blob in `fixtures/Level.sav` before porting:

```
PalGroupData:
  group_id: FGuid
  group_name: FString
  individual_character_handle_ids: TArray<PalInstanceId>   -- {guid, instance_id}, unchanged
  data: dispatched by GroupType:
    Guild:
      org_type: u8
      leading_bytes: [u8; 4]                                -- NEW, before base_ids
      base_ids: TArray<FGuid>
      unknown_1: i32                                        -- NEW, before base_camp_level
      base_camp_level: i32
      map_object_instance_ids_base_camp_points: TArray<FGuid>
      guild_name: FString
      last_guild_name_modifier_player_uid: FGuid            -- NEW
      guild_markers: TArray<PalGuildMarker>                 -- NEW
      tail: PostUpdate(chest roles, unknown_i32, admin, players-with-role,
                       role_permissions, trailing[4])
            or PreUpdate(admin, players, trailing[4])        -- probed: try PostUpdate,
                                                                 accept only on exact EOF,
                                                                 else rewind and read PreUpdate
    IndependentGuild: org_type, base_camp_level, camp_points array, guild_name,
                       player_uid, guild_name_2, last_online_real_time, player_name
                       (unchanged from the old reference)
    Organization:
      org_type: u8
      trailing_bytes: [u8; 12]                              -- kept opaque even upstream
```

Decoding the real Guild blob with this layout reaches an **exact clean EOF** at byte
4660 and recovers real content throughout: `base_camp_level=13`,
`guild_name` reading back as the guild's real 14-character name, and a
`PostUpdate` tail with one member and role 1. `crates/palsave/src/rawdata/group.rs` is now a direct port of this layout
(same MIT-license lineage as the rest of the project's format knowledge), not a
guess.

## What's still genuinely unknown

`OrganizationGroup::trailing_bytes` (12 bytes) and `GuildGroup::unknown_1` (i32) have
no confirmed semantic meaning — the upstream fork keeps them opaque too. One byte
within `Organization`'s trailer varies 2..8 sequentially across the 7 real samples
(looks like a small per-group sequence id), but round-trip correctness doesn't
require naming it, so it's stored as raw bytes rather than guessed at.

`base_ids` and `guild_markers` are empty (0 elements) in every sample seen so far, so
their *array element* wire format is exercised in code and by synthetic tests but not
cross-checked against a real non-empty instance.
