# ADR-003: Map key/value struct-type hints, and CharacterSaveParameterMap

## Status

Resolved. `crates/palsave/src/gvas/hints.rs` + threading a dotted `path: &str`
through `gvas::value`'s materialize functions. `crates/palsave/src/rawdata/
character.rs` decodes and round-trips all 137 real characters in
`fixtures/Level.sav` (`character_rawdata_round_trips_on_level_sav` in
`crates/palsave/tests/fixtures.rs`).

## The problem

`GvasFile::materialize` could reach `GroupSaveDataMap` (Guid-keyed) but fell back to
`Value::Raw` for every other map in the save —
`CharacterSaveParameterMap`,`ItemContainerSaveData`, `CharacterContainerSaveData`,
`BaseCampSaveData`, `GuildExtraSaveDataMap`. All of them have struct-typed keys and/or
values, and the wire format doesn't record which struct: that's a schema fact, not
serialized data (see the `TagExtra::Map` doc comment in `gvas/value.rs`, and
`PropertyType::MapProperty`'s tag-parsing branch in uesave-rs's `lib.rs`). Phase 2
shipped with a single hardcoded default (Guid for keys, generic property list for
values) that happened to be right for `GroupSaveDataMap` and wrong for everything
else — caught safely by the existing length-mismatch-falls-back-to-Raw guard, not
silently.

## The fix

`oMaN-Rod/uesave-rs` (the same fork credited in ADR-002.md) ships exactly the
per-path hint table the project plan called "PALWORLD_TYPE_HINTS-equivalent":
`games/palworld/mod.rs`'s `palworld_types()`, ~40 paths mapped to either
`StructType::Guid` or `StructType::Struct(None)` (a generic property list).
`gvas/hints.rs` is that table ported verbatim (two `&[&str]` lists, `STRUCT_HINTS`
and `GUID_HINTS`), looked up by `"{path}.Key"` / `"{path}.Value"`.

Making the lookup possible required threading a `path: &str` parameter through
`materialize_property` → `materialize_value` → `try_materialize_value`, built by
whoever calls `materialize_property` as `"{parent_path}.{property_name}"` — the same
convention the fork uses, which is what let the hint table be ported without
translation. `GvasFile::materialize` supplies the top-level property's own name as
the path root (e.g. `"worldSaveData"`); nested calls (through a `Struct::Properties`
list, or reaching into a Map's value) are the caller's responsibility to build
correctly, same as everything else about navigating the lazy tree.

One asymmetry worth remembering: unlisted paths still fall back to Guid-for-keys,
generic-struct-for-values — not an error. That default is correct often enough
(several real maps genuinely have bare-Guid keys) that failing loud on every unlisted
path would be noisier than useful; the existing length-mismatch guard still catches
the cases where the default is wrong.

## CharacterSaveParameterMap's RawData

Once the map itself materialized, its `RawData` decodes with `PalCharacterData` from
the same fork's `games/palworld/character.rs`: a nested, None-terminated GVAS
property list (a Pal or player's actual stats — `CharacterID`, `Level`, `Hp`,
`Talent_HP`/`Talent_Shot`/`Talent_Defense` (IVs), `FriendshipPoint`, ...), then 4
unknown bytes, a `group_id` Guid, and 4 trailing bytes. This matches the project
plan's original description of this path almost exactly — the plan (derived from
cheahjs's now-stale Oct-2024-vintage `character.py`) didn't have the 4 trailing bytes
after `group_id`; the same kind of small drift ADR-002.md found in `GroupSaveDataMap`.

Decoding real entry 5 in `fixtures/Level.sav` recovers a Female `ChickenPal` with
`FullStomach: 56.47`, `FriendshipPoint: 5210`, and a `group_id` matching the Guild
decoded in ADR-002.md — a Pal that belongs to that guild's base. All 137 real
characters in the fixture decode and round-trip byte-identically on the first try
with no further correction needed.

`rawdata::character::decode`'s nested property list reuses
`gvas::value::read_property_list` (now `pub(crate)` rather than `pub(super)`) instead
of duplicating the property-list walk — the same lazy, span-based indexing as every
other nested struct, just rooted in the RawData blob's own byte slice instead of the
save's.

## ItemContainerSaveData, and a generic-layer bug it exposed

`.worldSaveData.ItemContainerSaveData` (Phase 3's third named target) has two RawData
shapes at two paths, both in `rawdata/item_container.rs`, both from the same fork's
`games/palworld/items.rs`:

- `.Value.RawData` (`PalItemContainer`): the container's accepted-item-type
  permissions — two `Vec<u8>` lists plus a list of item static-id strings.
- `.Value.Slots[].RawData` (`PalItemContainerSlot`): one slot's `slot_index`, `count`,
  and `ItemId` (`static_id` + a two-Guid `DynamicId`).

Both end with a read-to-end unparsed tail rather than a fixed-width trailer, so
neither carries a hardcoded size that could silently mismatch after the next format
drift — and correspondingly neither has an exact-EOF check to make, unlike `group`
and `character`.

Wiring this up surfaced a real bug in the **generic** GVAS layer, not the Palworld
one: `gvas::value::read_array_body` returned early for a struct array with
`count == 0`, on the assumption that an empty array has no element-type tag to read.
Real data disagrees — the inner tag is written regardless, and 35 of the 1488
`Slots` arrays in `fixtures/Level.sav` are exactly that shape: a zero count followed
by a full, otherwise-unused `PalItemSlotSaveData` tag and nothing else (82 bytes
total: 4 for the count, 78 for the tag). uesave-rs reads the tag unconditionally; the
early return was this project's own addition. Those 35 properties were silently
falling back to `Value::Raw` — caught, as designed, by the length check rather than
producing wrong values. Fixed, with a synthetic regression test
(`materializes_empty_struct_array_including_its_inner_tag`).

With that fix: 1488/1488 containers and all 3062 slots decode and round-trip
byte-identically.
