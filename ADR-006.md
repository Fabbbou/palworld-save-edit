# ADR-006: Decoding a blob whose layout depends on data we don't have

## Status

Done. `crates/palsave/src/rawdata/dynamic_item.rs`. Gates green:
`dynamic_item_shapes_are_unambiguous` and `dynamic_item_ids_resolve_or_are_zero` in
`crates/palsave/tests/fixtures.rs`, over both worlds in the fixture corpus.

## The problem

`worldSaveData.DynamicItemSaveData` holds the per-instance state of items that have
any: armour durability, a gun's loaded rounds, which Pal is inside an egg. An
`ItemContainerSlot` has always carried the key to it — a `DynamicId` guid pair — and
nothing in this crate resolved that key.

The blob starts legibly:

```
Guid   created_world_id
Guid   local_id_in_created_world
FString static_id            e.g. "ClothArmor"
<payload>
```

and then stops being legible. The payload's shape depends on **what kind of item it
is**, and nothing in the blob says which kind that is. The game reads its own item
table to know. A save-file reader has no such table, and building one would mean
shipping a copy of Palworld's item database and keeping it current — the maintenance
burden this project exists to avoid.

Measured over two unrelated worlds with `examples/dump_blobs tails`, the payload takes
exactly three shapes:

| payload | fields | example |
|---|---|---|
| 12 bytes | `u32`, `f32` durability, `i32` rounds | `ClothArmor` → 150.0 |
| 24+n | the above, plus `u32`, `FString` ammo, `u32` | `Bow_triple` → `Arrow` |
| 40+n+m | `u32`, `FString` species, `FString`, 28 bytes | `PalEgg_Normal_03` → `Deer` |

Total blob lengths are useless as a discriminator — 37 distinct values across 351 blobs
— because the embedded `static_id` varies. Stripping the known prefix first collapses
that to three shapes, which is what made the problem tractable at all.

## What was rejected

**Guess from `static_id`.** Match `PalEgg_*`, treat names containing `Bow`/`Gun` as
weapons, and so on. This is how it would be done with a name table, and it is exactly
the "plausible-looking wrong answer" `CLAUDE.md` forbids: the first item whose name
doesn't fit the pattern gets another item's durability reported against it, silently.

**Decode nothing; keep the payload opaque.** Safe, and it would still have unblocked
migration, since carrying a row across worlds doesn't require understanding it. But it
delivers no user-visible information at all — the slot already knows the item's name,
so an opaque payload adds nothing to a screen.

**Pick the first shape that parses.** Cheap, and wrong in exactly the cases that
matter. A shape can "parse" while leaving bytes unconsumed, which means it read the
wrong fields and happened not to run out of buffer.

## The decision

Try every shape, require each to consume the payload **to the byte**, and accept the
result only when exactly one fits.

- Ending early is not a match. Running over is not a match.
- If **more than one** shape fits, the answer is `Opaque` — a refusal, not a coin flip.
- If none fit, likewise `Opaque`.

Every shape, `Opaque` included, re-encodes byte-identically, so this module cannot
alter a byte it did not understand.

The ambiguity case is not hypothetical hand-waving: a `WithAmmo` payload whose ammo
name is 18 characters is 42 bytes, and so is the shortest possible `Egg`. Nothing in
the format prevents that collision. What makes exact-fit classification sound is not
that collisions are impossible, but that they are *detected*.

## Why this is safe to rely on

`dynamic_item_shapes_are_unambiguous` asserts that no blob in any available world fits
two shapes at once, and prints the shape census per world. All 568 blobs across the two
worlds classify cleanly:

```
Level.sav:        16 durability, 17 with-ammo, 318 egg, 0 opaque
friend/Level.sav: 39 durability, 32 with-ammo, 146 egg, 0 opaque
```

That census is the early-warning system. A future game version that adds a fourth
payload shape shows up as a **rising `opaque` count** — a number in a test, not a wrong
durability on someone's screen. A version that makes the collision real shows up as a
failing assertion. Either way the affected item degrades to "no dynamic state known",
which the UI already renders as blank.

The second gate covers the join rather than the decode. Most item slots carry an
all-zero `DynamicId`, because one plank of Wood is like any other — so "this item has
no dynamic state" and "the join is broken and everything is `None`" look identical on
screen. `dynamic_item_ids_resolve_or_are_zero` separates them by counting the third
category: a *non-zero* id matching no row. It must be empty, and is (228 and 145 slots
resolve, 0 dangling).

## Consequence for the UI

`SlotView.durability` and friends are `null` for most items, and `null` means "not
applicable", never "lookup failed". The Pals & items screen renders that as a blank
cell rather than a dash or a zero, because a stack of Wood having no durability is not
missing information.

## Related

This is the second decoder in the crate written from measurement rather than ported
from `oMaN-Rod/uesave-rs` (ADR-002.md). The first, `rawdata/character_container.rs`,
went the other way on a similar question: its leading 16 bytes look exactly like a
`player_uid` and older references describe them as one, but all 301 slots in a
two-player world carry the same value, so the field cannot identify an owner. There the
honest move was to *not* name a field the data contradicts. Here it was to name three
shapes the data supports, and refuse when it doesn't.
